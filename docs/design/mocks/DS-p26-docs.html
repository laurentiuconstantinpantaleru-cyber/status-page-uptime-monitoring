How monitoring works

What Campus Uptime checks, when it opens and closes an incident, and how the numbers on the status page are calculated.

  • Incidents
  • Maintenance windows

Checks

Each monitor points at one URL. A worker checks it every 5 minutes by default; an admin can pick any interval from 1 to 60 minutes. A check waits up to 30 seconds for an answer, long enough for a sleeping free host to wake up.

HTTP status

The answer must have the expected status code, 200 unless the monitor says otherwise. A 5xx or any other code fails the check.

Keyword

If the monitor has a keyword, the page must contain it exactly, with the same capital letters. A missing keyword fails the check.

Response time

If the monitor has a threshold, a slower answer marks it Degraded. It still counts as up.

TLS certificate expiry

For HTTPS monitors the worker reads when the certificate expires and warns 30 days and again 7 days before.

A failed check records why: timeout, 5xx, unexpected status, missing keyword, DNS, TLS or connection. Raw checks are kept for 7 days, then summed up per hour and per day.

Incidents

One failed check is not an incident: networks blip. An incident opens only when the failure is real.

  1. A worker's check fails.
  2. A second, independent worker checks the same URL straight away and must fail too.
  3. After 2 consecutive confirmed failures the monitor is Down and an incident opens, with its cause.
  4. After 2 consecutive successful checks the incident closes by itself.

When the worker is the problem

If most of one worker's monitors fail at once while the other worker reaches them fine, the fault is that worker's network (for example its DNS), not the sites. No incident is opened, and admins see a worker fault in the dashboard.

Updates

People on the team post updates as an incident moves through Investigating, Identified, Monitoring and Resolved. They appear on the status page.

Maintenance windows

Planned work should not look like an outage. During a maintenance window checks keep running, but no alerts are sent and downtime does not count against uptime.

  • Scheduled: pick a start and an end in the calendar.
  • Quick: one click starts maintenance for 15, 30 or 60 minutes, for example right before a deploy.

While a window is open the status page shows the monitor as Maintenance.

How uptime is calculated

Uptime comes from incidents, not from counting checks, so a monitor checked every minute and one checked every hour are measured the same way.

uptime = available time / (total time − maintenance time)

Downtime that falls inside a maintenance window is not counted. An incident that crosses midnight or the end of a month counts in each period only for the part inside it.

Example: November

An incident runs from 31 October 23:00 to 1 November 02:00 UTC, and maintenance runs on 1 November from 00:00 to 01:00. November has 720 hours. Maintenance takes 1 hour, leaving 719. Of the incident, only 1 November 00:00 to 02:00 is in November, and its first hour is maintenance, so 1 hour counts as down.

(719 − 1) / 719 = 99.86%

Alerts and escalation

When an incident opens, the primary contacts get one alert by email or Telegram, and one more when it is resolved: no alert for every failed check.

Each alert says which monitor and URL failed, the HTTP code or error, the cause, how long since the last good check, and has a link to acknowledge it.

Escalation

If nobody acknowledges the alert within 15 minutes, the secondary contact is alerted too. Organization admins can set this time up to 1 hour. Acknowledge from the link in the alert or in the dashboard.
